# ReproProof PRD v2.0 评审

> 评审对象：`reproof-prd-v2.html`  
> 评审日期：2026-10-22  
> 总评：8.5/10，可以作为开发基线，但有 8 个问题必须在开发前修正。

## 一、已经改好的部分

1. 目标用户从“泛 AI 实验室”收缩为 Artifact 提交实验室；
2. 产品形态从 Web 改为 CLI + GitHub Action + HTML/Markdown 报告；
3. 规则从 10 条收缩为 6 条；
4. 明确规则边界和“不做”的能力；
5. 补充竞品分析和三层差异化；
6. 补充安全边界、测试集、指标和基线对比；
7. 演示脚本和三天计划已经具备可执行性。

## 二、必须修正的问题

### 1. 不可靠的数据引用

PRD 中写“超过 70% 的研究者无法复现他人实验，50% 无法复现自己的实验”，必须补充权威出处，否则删除。比赛评委可能直接追问来源。

建议改成有出处的表述，或使用：

> 可复现性失败在机器学习研究中长期存在，常见原因包括缺少随机种子、依赖未锁定、数据划分不当和运行命令缺失。

### 2. Artifact 失败与论文录用的关系不准确

PRD 写“Artifact 不通过会影响论文录用”。这不一定成立。

Artifact Evaluation 在多数顶会是独立流程，结果通常影响 Artifact Badge、复现性认证和声誉，不直接决定论文录用。

建议改为：

> Artifact 不通过会影响复现性徽章、论文可信度和后续复用，部分会议和期刊还可能影响 artifact track 的结果。

### 3. 评分模型不应预测录用

“85-100 大概率通过”“0-49 大概率被拒”容易被质疑，因为评分没有校准。

建议改成：

> 评分是仓库内部可复现性风险指标，不代表会议或期刊的实际评审结果。

同时把“可以提交/不建议提交”改成“风险较低/建议优先修复高风险问题”。

### 4. 论文-代码一致性必须有无 LLM 降级方案

规则 6 依赖通义千问 API。现场网络或密钥失败时，整个差异化功能会不可用。

必须增加：

- 无 LLM 时使用正则和关键词提取；
- 预置一个演示论文与仓库的缓存结果；
- LLM 只做增强，不作为核心链路的唯一依赖；
- 对外明确“结果需要人工确认”。

### 5. “唯一差异化”表述过强

BenchSherlock、ReproRepo 等已经在做复现审计和论文-代码一致性研究。不能说“竞品几乎没有”或“独一无二”。

建议改为：

> 多数现有工具是单次仓库审计或研究原型。ReproProof 的产品化差异是嵌入 PR 流程、提供可解释报告，并把论文声明与代码实现做有限对齐。

### 6. GitHub Action 不能只停留在模板

如果产品核心是“自动运行的质量 Gate”，就必须至少交付一个真实可运行的 Action 示例：

- `action.yml`；
- 安装方式；
- 运行命令；
- 退出码规则；
- `fail-on: high`；
- PR 评论生成。

否则评委可以认为“自动 CI”只是叙事，不是实现。

### 7. 雷达图的实现方式与依赖不匹配

技术栈写 Jinja2 + 内联 CSS，但要画六维雷达图，缺少图表库或 SVG 实现方案。

首版建议：

- 用纯 SVG 画雷达图；
- 或改成六个横向进度条；
- 或删掉雷达图，保留评分卡。

不要因为图表美观增加前端框架。

### 8. 三天计划和验收标准还需要收紧

PRD 的 Day 3 上午同时做规则 6、Action、演示仓库和修复误报，风险仍然偏高。

建议把完成时间提前半天：

- Day 1 晚：规则 1-3 可运行；
- Day 2 中午：规则 4-5 可运行；
- Day 2 晚：HTML/Markdown 报告、初步测试；
- Day 3 上午：规则 6 + Action + 演示仓库；
- Day 3 下午：冻结代码，只做视频、PPT、技术方案和打包。

## 三、建议补充的内容

### 1. 真实用户验证

至少访谈：

- 3 名正在准备论文投稿的 AI 研究生；
- 1 名导师；
- 1 名会议 Artifact Evaluation 审稿人或熟悉 AE 的同学。

记录他们目前如何检查可复现性，以及是否愿意接入 Git 工作流。

### 2. 文件分发方式

比赛评委不一定能运行 `pip install`。建议提供：

- 完整源码 ZIP；
- 一键运行脚本；
- 预装依赖说明；
- `python -m reproof` 或 `python reproof.py` 的兼容入口；
- 一份演示仓库和论文；
- 录屏备份。

### 3. 真实测试仓库

5 个仓库全部人工注入缺陷会有“自测自过”的质疑。建议至少加入 1-2 个真实公开小型仓库，说明检测结果和误报。

### 4. 每条规则的验收标准

例如：

| 规则 | 必须识别 | 不允许 |
|---|---|---|
| 规则 4 | scaler 早于 split 的 3 种模式 | 把正常 train-only fit 误报 |
| 规则 6 | 数据集名和指标名不一致 | 对没有证据的语义做结论 |

### 5. 误报控制

必须明确：

- 规则结果都带置信度；
- 高置信度才默认阻塞；
- 中低置信度只做提示；
- 用户可忽略规则/文件；
- 报告保留原文证据。

## 四、总体建议

PRD v2 的产品方向、目标用户、CLI 形态和技术亮点均已成立。现在不应继续改产品范围，而应把以下三件事作为冻结后的唯一目标：

1. `reproof audit . --paper paper.pdf` 在 5 个仓库上稳定运行；
2. 输出一份可解释的 HTML 报告；
3. 提供一个可运行的 GitHub Action 示例和 `pr-comment.md`。

## 五、最终结论

**可以开始开发，但先做 8 项修正：**

1. 补或删除 70%/50% 数据来源；
2. 修正 Artifact 与论文录用的关系；
3. 把评分改成风险指标，不做录用预测；
4. 为规则 6 增加无 LLM 降级；
5. 收敛“唯一/没有竞品”表述；
6. Action 必须可运行，不只是模板；
7. 雷达图改用 SVG 或进度条；
8. Day 3 上午完成规则 6 和 Action，下午只做材料。

完成这些后，PRD v2 可以作为最终开发基线。
